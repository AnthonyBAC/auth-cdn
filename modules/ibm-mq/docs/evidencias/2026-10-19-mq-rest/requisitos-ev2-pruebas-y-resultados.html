  2. Guardar el MsgId devuelto por IBM.
  3. Examinar ese mismo MsgId mediante GET, sin retirarlo.
Resultado esperado

IBM acepta el envío con HTTP 201, asigna un MsgId y devuelve el mismo evento con HTTP 200 en la lectura.

POST 201 y GET 200. El MsgId de publicación coincide con el leído, y el encabezado persistence indica persistent.

Alcance: La prueba demuestra uso real de IBM MQ como broker. No se usa una cola en memoria para sustituirlo.

2. Mensajería asíncrona

Programar la tarjeta guarda el trabajo en Supabase. Al llegar la fecha, el productor publica el evento en IBM; el consumidor cloud lo captura y process_reminder_event crea el aviso. La respuesta al usuario no espera a esa entrega futura.

Prueba realizada

  1. Programar un recordatorio con PATCH autenticado mediante JWT.
  2. Esperar notifyAt y ejecutar el procesamiento cloud.
  3. Consultar los avisos del usuario y relacionar eventId entre outbox, inbox y notificación.
  4. Repetir con Supabase Cron sin invocar tick manualmente después de programar.
Resultado esperado

La programación responde 200. Después aparece un aviso del usuario, con outbox PUBLISHED, inbox DONE y recordatorio PROCESSED. La entrega autónoma no depende de un trabajador local.

Programación 200 y aviso normal visible. En el ensayo autónomo, el mismo eventId aparece en outbox PUBLISHED, inbox DONE y la notificación; el recordatorio preventivo queda PROCESSED.

Volver a la matriz

3. Mensajería síncrona

El usuario solicita un resumen y espera la respuesta. Vercel publica en AUTHCDN.SUMMARY.REQUEST.Q; el responder cloud contesta por AUTHCDN.SUMMARY.REPLY.Q. requestId identifica la operación y CorrelId enlaza la respuesta con el MsgId de la solicitud.

Prueba realizada

  1. Enviar POST autenticado al resumen de un tablero.
  2. Comprobar estadísticas, requestId y correlación entre las dos colas.
  3. Enviar solicitudes simultáneas y verificar que no se mezclan sus respuestas.
  4. Demorar solo el tablero de ensayo hasta agotar la espera y retirar luego esa demora.
Resultado esperado

En operación normal, HTTP 200 con el resumen correcto. Cada respuesta corresponde a su solicitud. Si no llega a tiempo, HTTP 504; tras resolver la demora, una nueva solicitud vuelve a responder 200.

Resultado obtenido · Correcto en el alcance descrito

Resumen 200 con totalActive=3 y pending=3 para el estado de ese tablero en ese momento. CorrelId de respuesta igual al MsgId de solicitud. La demora produjo 504 GATEWAY_TIMEOUT y la petición posterior devolvió 200.

Alcance: El timeout se provocó con una demora SQL restringida al tablero de ensayo. La duración medida de extremo a extremo fue 28.520 ms; incluye trabajo previo y red. La foto de resumen corresponde a una ronda posterior con ocho tarjetas y no se usa para justificar los conteos de la primera respuesta.
